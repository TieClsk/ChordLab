# 测试策略：TDD + 用户体验测试 / Testing strategy

ChordLab 采用**测试驱动开发（TDD）**，并且每个 Sprint 都安排**用户体验（UX）测试**。目标是在最短时间内发现问题：代码层面每次提交都有反馈，体验层面每个 Sprint 至少两次反馈。

## 1. TDD 工作循环

每个用户故事都按下面的顺序推进，PR 的提交历史要能看出这个顺序：

1. **从验收标准写测试**：把 Issue 里每条验收标准翻译成一个或多个测试。先提交 `test(scope): ...`，此时测试应当失败（红）。
2. **最少实现让测试通过**（绿）：提交 `feat(scope): ...`。
3. **重构**：在测试保护下整理代码，提交 `refactor(scope): ...`。
4. 不能自动化的验收标准（手感、听感、易懂程度）写进本 Sprint 的 **UX 测试脚本**（见第 4 节），由产品负责人验证。

> 规则：没有失败测试，不写产品代码。修 bug 也一样：先写一个能复现 bug 的测试。

## 2. 测试金字塔（按层）

| 层 | 测什么 | 工具 | 何时运行 |
| --- | --- | --- | --- |
| 引擎单元 | DSP、调度、声部、命令编解码 | `cargo test` | 每次提交（CI） |
| 引擎不变量 | 音频线程零分配、采样级调度、块大小无关 | `cargo test`（计数分配器等） | 每次提交 |
| 引擎属性测试 | 任意合法工程都不 panic、不出 NaN、输出有界 | `proptest` | 每次提交 |
| 黄金音频 | 固定工程的渲染结果与基准一致（哈希 + 允许误差） | `cargo test` + `tests/golden/` | 每次提交 |
| 双目标一致性 | 原生与 WASM 输出逐采样一致 | `experiments/wasm-parity` | 每次提交 |
| 性能预算 | 64 声部每块 < 10% 预算；导出 > 50× 实时 | `chordlab-engine bench`（阈值断言） | 每次提交 |
| 乐理 / 推荐 | 和弦解析、排序、级数、推荐概率 | Vitest | 每次提交 |
| 界面组件 | 交互逻辑、可访问性、中英文文本完整 | Vitest + Testing Library | 每次提交 |
| 端到端（Web） | 完整用户流程，在真实 Chromium 中发声 | Playwright | 每次提交 |
| 端到端（桌面） | 应用启动、IPC、原生音频链路 | 冒烟脚本（Xvfb）；Windows/Linux 上用 tauri-driver | 每次提交 / 预览构建 |
| 识别准确率 | 和弦 / 调 / BPM 的 mir_eval 指标不得退步 | Python 评测脚本 | 分析相关 PR |
| 音乐正确性 | 节拍对齐、时值、力度：例如回声恰好落在八分音符网格上 | `cargo test`（S0 回顾新增） | 每次提交 |
| 数值健康 | 音频路径不产生 NaN / 非规格化数 | `cargo test`（#48） | 每次提交 |
| **用户体验** | 好不好用、好不好听、看不看得懂 | 人工测试会话（第 4 节） | 每个 Sprint 2 次 |

## 3. 覆盖与门禁

- CI 任一检查失败，PR 不能合并（main 分支保护）。
- 新增或修改的引擎代码必须有对应测试；跳过测试要在 PR 中写明理由。
- 准确率、性能这类指标型测试有阈值，并在 PR 描述中报告前后数值。

## 4. 用户体验测试（由产品负责人执行）

### 节奏

| 时间点 | 内容 | 产出 |
| --- | --- | --- |
| Sprint 中期 | **预览测试**：用 CI 构建的预览安装包，按测试脚本完成任务 | 每个问题一个 `type:ux-feedback` Issue |
| Sprint 评审 | **验收测试**：逐条验证本 Sprint 故事中“需人工验证”的验收标准 | 在故事 Issue 中勾选或打回 |

### 怎么拿到测试版本

- 每个 PR 和 main 上的每次提交，CI 都会构建桌面预览包（macOS / Windows / Linux），在 Actions 运行页面的 Artifacts 中下载。
- 每个 Sprint 的 UX 测试 Issue 会直接给出对应构建的链接。
- macOS 预览包未签名：第一次打开请右键 → 打开。

### 测试脚本格式

每个 Sprint 一个 Issue：`[UX] S<n> 用户体验测试`，内容包括：

1. **背景**：本轮要验证什么。
2. **任务清单**：以用户目标描述，不告诉你点哪里。例如：“弹出 Am 和弦，然后找到它后面常接的和弦并试听”。
3. **每个任务记录**：是否完成、大约用时、卡住的地方、主观评分（1–5）。
4. **固定交互场景**（S0 回顾新增）：长按、快速连按、按住时切到别的窗口。
5. **整体感受**：最喜欢 / 最困惑 / 最想要的一点。
6. **听感检查**（涉及音频时）：有无爆音、延迟感、音色是否自然、节奏是否在拍上。

### 反馈如何进入开发

- 每条问题用 “UX 反馈” 模板单独开 Issue（标签 `type:ux-feedback`）。
- 下一次 Sprint 计划会上，与其他待办一起排优先级；严重问题（无法完成任务、刺耳爆音）直接进入当前 Sprint。
- 能自动化复现的问题，修复时先补测试（回到第 1 节）。
